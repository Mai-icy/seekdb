# SF500: bounded data preparation and native GPU aggregation

Experiment on 2026-10-23, isolated port-2886 seekdb instance on the existing
RTX 5880 host. Native server/bridge binaries are the previous profiling/packing
stage; this stage changes the Python sidecar and preparation tools.

## Scope and data ownership

The existing source is `/data/wuhao.xwh/duckdb-sirius-data/tpch_sf500.duckdb`
(140,138,786,816 bytes, about 130.5 GiB). It is opened **read-only** with the
already installed DuckDB 1.5.6. Its size and nanosecond mtime are recorded and
checked after import. No source database copy, regeneration, full CSV export,
Parquet replica or persistent GPU table cache is created.

| Source table | Full row count | seekdb target |
|---|---:|---|
| supplier | 5,000,000 | test.sirius_sf500_supplier |
| customer | 75,000,000 | test.sirius_sf500_customer |

Each target contains only `(id BIGINT PRIMARY KEY, grp BIGINT NOT NULL,
amount DOUBLE NOT NULL)`: original primary key, nation key and account balance
in integer cents. The conversion is `CAST(acctbal * 100 AS BIGINT)` in DuckDB,
then exact integer CSV values loaded into DOUBLE. These values and aggregate
sums are below 2^53, allowing exact validation against the original DECIMAL
source. This does not add general DECIMAL SUM support to the native adapter.
Both full tables produce 25 groups. These are **SF500-derived full-table
operator tests**, not a run of all TPC-H tables or the 22-query suite. Lineitem,
orders, strings and unrelated columns remain solely in the original database.

For the current operator coverage, this avoids preparing hundreds of gigabytes
that the adapter cannot yet execute. Future join support should add only the
required columns and relations, reusing this read-only source.

## Bounded, resumable preparation

`unittest/sql/sirius/prepare_sf500.py` writes at most one million rows per CSV
and deletes it after each load. `--workers 4` permits four concurrent files and
independent seekdb connections; scheduling occurs in bounded rounds. The file
limit is 64 MiB each (256 MiB at four workers); this data actually needs less
than 18 MiB each. DuckDB has a shared 2 GB memory limit, four threads and disabled
temporary disk spilling. `LOAD DATA LOCAL INFILE` is enabled only for the
explicit import connections to the trusted test instance.

The importer enforces a configurable free-space reserve (default 100 GiB) and
filesystem growth budget (default 8 GiB), leaving 1 GiB headroom for in-flight
loads. These checks measure the staging filesystem: place staging and the
isolated seekdb store on that same filesystem, as in this experiment. They are
polling guards, not filesystem quotas; seekdb logs/preallocation and unrelated
writers also affect measured free space.

Each completed range records row counts, CSV size, times and available disk in
an atomically replaced manifest. Resume checks source identity and chunk layout,
skips exactly the recorded ranges even when completions are out of order, and
clears only unrecorded ranges in the manifest-owned target before retrying.
LOAD DATA is not globally atomic. The initial interrupted customer chunk was
successfully retried using this mechanism. A per-source import lock prevents
concurrent runs in the same directory. Use a dedicated target; do not write to
it externally during import. New runs refuse to overwrite an existing target.

Final validation compares all 25 `(nation, COUNT(*), SUM(cents))` rows against
DuckDB, as well as each imported primary-key range's count. Manifests retain the
source oracle and source fingerprint. No CSV files are retained.

```sh
# Use a Python environment containing compatible DuckDB, PyMySQL and PyArrow.
export SEEKDB_PORT=2886
python unittest/sql/sirius/prepare_sf500.py \
  --database /data/wuhao.xwh/duckdb-sirius-data/tpch_sf500.duckdb \
  --directory /data/wuhao.xwh/seekdb-sirius-sf500-20261023 \
  --source-table customer --target sirius_sf500_customer --workers 4
# Only after interruption: repeat the same command with --resume.
```

The host's compatible DuckDB module was reused through `PYTHONPATH` from
`duckdb-sirius-upstream/sirius/.pixi/envs/default/lib/python3.14/site-packages`;
no second DuckDB environment or database was installed.

An initial incremental-direct-load hint was accepted by SQL but did not improve
throughput. Inspection of this seekdb revision's CSV executor showed the single
partition implementation being selected. The final tool uses `NO_DIRECT` and
independent bounded connections, rather than claiming that hint enabled a direct
load fast path. Historical chunks retain their actual hint in the manifest.

## GPU execution larger than 512 MiB

Start the sidecar with `--host-pin-mib 16 --warmup --native-chunk-mib 128`.
The native seekdb scan, MVCC and transport are unchanged. Each GPU fragment
receives approximately 128 MiB of decoded projected columns, computes grouped
partial SUM/COUNT, and releases its fragment before the next one runs. The
sidecar merges the small partial results on CPU. At a boundary, one extra native
frame (maximum 16 MiB) can exceed the target. The 512 MiB per-fragment guard and
1 MiB result bounds remain. An exact last boundary may execute an empty final
fragment. NULL keys/sums and grouping-only queries are handled explicitly.

Customer SUM/COUNT sends 1,218,750,000 decoded bytes; COUNT sends 609,375,000.
Both exceed the former total-input limit, without materializing the full table
in host or GPU memory. The 16 MiB pinned receive buffer is reused only after
synchronized copy acknowledgment. It stores no reusable table snapshot.

This is sequential GPU partial aggregation with a small CPU final merge. Scan,
transfer and GPU compute are not overlapped across fragments. The native
60-second query transport deadline is unchanged; chunking does not establish
support for arbitrarily long queries. High-cardinality outputs still hit the
1 MiB limit. General floating-point SUM can differ because reduction order
changes; non-finite partial/merged sums return an error.

## Validation and measurement

The new chunk suite covers eight boundary/NULL/merge/overflow/size cases. The
existing nine protocol tests and sixteen SQL/transaction checks also pass.
A real 5-million-row, four-SUM, 1,000-group query spans two GPU fragments and
matches CPU; it was run during import, so its timings are correctness evidence
only. Full SF500 target correctness is checked against DuckDB during preparation
and CPU results for every benchmark query. Sidecar logs record actual native
input row counts and fragment counts.

Performance results and disk accounting are recorded below after import and
major compaction. Times include seekdb scan, packing, transfer, GPU work, CPU
partial-result merge and SQL execute/fetch. Python validation sorting is excluded.
No seekdb profiling counters are enabled. First executions are recorded
separately; repeated runs use warm OS/database caches, with no global cache flush.

### Results

Major compaction completed at 12:12:07 local time (`IDLE`, `IS_ERROR=NO`, frozen
SCN 1792728656882593025). All modes use the same
`OPT_PARAM('rowsets_max_rows' 1024)` scan hint and `USE_HASH_AGGREGATION`.
CPU1/GPU use `PARALLEL(1)`; CPU8 uses `PARALLEL(8)`. Each benchmark rotates the
three modes; seven measured repetitions follow one first execution per mode.

128 MiB fragments, pinned receive and startup warmup:

| Full table / query | CPU1 | CPU8 | GPU | Speedup vs CPU1 |
|---|---:|---:|---:|---:|
| supplier 5M: SUM + COUNT | 155.32 ms | 32.75 ms | 84.55 ms | 1.84× |
| supplier 5M: COUNT | 132.49 ms | 29.17 ms | 60.97 ms | 2.17× |
| customer 75M: SUM + COUNT | 2,216.13 ms | 371.33 ms | 1,227.91 ms | 1.80× |
| customer 75M: COUNT | 2,022.65 ms | 330.02 ms | 861.04 ms | 2.35× |

CPU8 remains faster for every case. The >=2× observation is relative to the
serial CPU plan for COUNT, not a general GPU win over parallel seekdb. The full
customer runs validate inputs beyond the old 512 MiB limit: logs show nine GPU
fragments for SUM/COUNT and five for COUNT with 128 MiB targets.

Additional sequential runs vary only the fragment target, with three measured
repetitions per mode/query:

| Fragment target | Customer SUM + COUNT, GPU | Customer COUNT, GPU | Fragments, SUM / COUNT |
|---|---:|---:|---:|
| 64 MiB | 1,253.62 ms | 898.53 ms | 18 / 9 |
| 128 MiB (seven-repeat baseline) | 1,227.91 ms | 861.04 ms | 9 / 5 |
| 256 MiB | 1,265.38 ms | 858.70 ms | 5 / 3 |

The small sequential differences do not establish a stable performance ranking.
128 MiB is retained as a bounded working configuration; doubling it showed no
clear benefit. Global defaults remain unchanged (chunking is opt-in). Across
these SF500 runs, all 144 mode/query executions including first executions
matched their CPU oracle; both target tables were independently validated
against DuckDB. These are warm-storage measurements, not a cold-cache or
cold-process SF500 claim.

```sh
# Start sidecar with --host-pin-mib 16 --warmup --native-chunk-mib 128.
# Enable SEEKDB_SIRIUS_NATIVE=1 before starting the isolated seekdb instance.
export SEEKDB_PORT=2886
python unittest/sql/sirius/native_benchmark.py \
  --table sirius_sf500_customer --scan-batch-rows 1024 --repeats 7 \
  --output customer-chunk128-batch1024.json
# Change the target to sirius_sf500_supplier for the smaller full-table check.
```

### Space and retained state

- Peak supplier CSV: 17,489,117 bytes (16.68 MiB).
- Maximum customer CSV: 18,491,111 bytes; four-worker simultaneous upper bound
  for this data: 73,964,444 bytes (70.54 MiB). No CSV remains.
- The seekdb data file remains **10,737,418,240 bytes (10 GiB)**, its pre-existing
  allocation. The projected tables fit inside it, without file expansion.
- Lowest sampled filesystem free space during import: 722,453,647,360 bytes
  (~672.84 GiB); final: 726,189,731,840 bytes (~676.32 GiB). Final free space is
  about 93.4 MiB below the initial sample after log recycling. This is filesystem
  accounting, **not** the tables' physical size: they consume existing allocated
  capacity, and transient redo/compaction/log files affect the samples.
- `information_schema.TABLES` had stale row estimates and zero size statistics;
  those values are retained as diagnostic evidence, not used as row counts or
  table-size claims. `V$OB_SSTABLES` includes retained versions and is not summed
  as a unique physical-byte footprint.
- Both seekdb target tables and manifests remain for reuse. The source DB
  fingerprint is unchanged. Our seekdb and sidecar processes were stopped;
  both GPUs returned to 2 MiB reported usage. Borrowed Sirius source is clean.
